# Module — промпты для Claude Code

Файл содержит: стартовый промпт (вставить первым), роадмап коротких промптов по фазам
и правила работы с репозиторием. Стартовый промпт длинный намеренно — он один раз
фиксирует то, что потом не придётся повторять в каждом сообщении.

---

## ПРОМПТ №0 — вставить первым в пустом репозитории

```
Мы делаем с нуля терминальную idle-игру «Module» — симулятор энергокомпании с атомной
станцией. Ты будешь вести этот проект долго, поэтому первым делом мы фиксируем
спецификацию и скелет, а не пишем геймплей.

## Что это за игра

Игрок управляет энергокомпанией: реактор, продажа электроэнергии на рынке, финансы,
поимённый персонал с правами доступа и профсоюзом. Игра бесконечная, идёт «сама»,
проигрыш возможен и болезнен. Основной способ игры — открыл терминал, отдал приказы,
закрыл; при следующем запуске игра честно досчитывает пропущенное время.

## Жёсткие требования (не меняй их без моего явного согласия)

1. Полностью в терминале. Интерфейс — Textual. Запуск одним словом: `module`.
   Короткий алиас `mdl`.
2. Ставится в Arch Linux через PKGBUILD. Зависимости — ТОЛЬКО те, что есть в
   официальных репозиториях (проверено: python-textual, python-rich, python-msgpack,
   python-platformdirs, python-pytest есть; plotext и ptpython — НЕТ, на них не
   закладываться, графики рисовать своими виджетами Textual).
3. Обновление игры никогда не теряет прогресс. Это требование номер один по
   важности, см. раздел про сохранения.
4. Автосохранение, атомарное, без шансов получить битый файл.
5. Игра не работает в фоне. Пока процесс закрыт — время не идёт, ничего не считается,
   уведомлений на рабочий стол нет вообще. Причина: я студент, и игра не должна
   отвлекать меня во время учёбы. Пропущенное время досчитывается при запуске.
6. Внутри игры НЕТ блокирующих ожиданий. Любое действие (продажа акций, ремонт,
   найм, поставка топлива) — это приказ с длительностью, который исполняется в
   игровом времени, пока я занимаюсь другими делами. UI не ждёт никогда.
7. Скоростью игрового времени управляю я: пауза, 1x, 5x, 50x, «промотать до
   следующего события». Промотка мгновенная по реальному времени.

## Инварианты, которые нельзя нарушать

- `core/` не импортирует `ui/`. Симуляция обязана полностью тестироваться без
  терминала. Если для теста геймплея нужен Textual — архитектура сломана.
- Симуляция детерминирована: одинаковый seed + одинаковые действия = одинаковый
  результат, до последнего числа. Все случайности идут через `rng.stream("имя")` —
  отдельный поток на каждую подсистему. Это чтобы добавление нового события не
  сдвигало последовательности старых и старые сейвы продолжали считаться так же.
  Голый `random.random()` в коде игры запрещён, добавь проверку в тесты.
- Фиксированный шаг симуляции: 1 тик = 1 игровой час. UI перерисовывается независимо
  от тиков.
- Догон должен считать не меньше 200 000 тиков в секунду (это ~23 игровых года в
  секунду). Пиши ядро с оглядкой на это: никаких аллокаций и словарей в горячем цикле.
  Если простой огромный — считай честно, но покажи прогресс-бар.
- Каждое случайное событие ОБЯЗАНО иметь причину, выведенную из состояния мира: износ
  оборудования, просроченное ТО, усталость смены, недовольство персонала, цена на
  рынке, срок контракта. События «просто так» запрещены. В журнале для каждого
  события пишется, почему оно случилось, и какой параметр это предсказывал. Игрок
  должен иметь возможность научиться их предвидеть.

## Сохранения и обновления — самая важная часть

- Один файл сейва: `~/.local/share/module/save.json` (msgpack если станет тяжело),
  в нём поле `schema_version` (целое).
- Каждое изменение структуры = новый файл `migrations/vNNN.py` с функцией
  `migrate(data: dict) -> dict`, поднимающей версию ровно на единицу. При загрузке
  применяется вся цепочка от версии файла до текущей.
- Старую миграцию НИКОГДА не редактируют. Только добавляют новую.
- В `tests/fixtures/saves/` лежат настоящие сейвы каждой версии. Тест грузит каждый
  из них, прогоняет миграции и проверяет, что игра запускается и симуляция идёт.
  Этот тест — главный страж требования «обновление не теряет прогресс».
- Запись атомарная: во временный файл рядом, fsync, `os.replace`. Плюс кольцо из
  5 бэкапов `save.json.1..5` и команда `module save restore`.
- Отдельный файл `~/.local/share/module/meta.json` — метапрогресс между партиями,
  переживает удаление партии. В нём хранится переходящий долг (см. ниже).

## Экономика и провал

- Рынок электроэнергии: сутки-вперёд и спот, суточный и сезонный профиль цен,
  пиковые часы, конкуренты, эластичность спроса.
- Контракты: долгосрочные PPA с фиксированной ценой против спота — игрок сам выбирает,
  сколько хеджировать. Штрафы за недопоставку.
- Топливо: контракты на обогащённый уран с лагом поставки, цена ходит, кампания
  топлива около 18 месяцев.
- Финансы: кредиты со ставкой, зависящей от кредитного рейтинга, ковенанты,
  облигации, амортизация, налоги, страховка, обязательный резервный фонд на вывод
  из эксплуатации.
- Банкротство: если обязательства больше активов и долг не обслуживается — внешнее
  управление, распродажа активов, конец партии.
- ОСТАТОК ДОЛГА ПЕРЕХОДИТ В СЛЕДУЮЩУЮ ПАРТИЮ через meta.json. Новая партия
  начинается с этим долгом на балансе.
- Выход есть: официальная процедура банкротства списывает долг, но ценой — репутация
  на дне, кредитная ставка кратно выше, часть рынков и контрактов закрыта на
  несколько игровых лет. Это не поблажка, это цена.

## Физика реактора (PWR, упрощённо, но по-настоящему)

- Точечная кинетика с запаздывающими нейтронами. Реактивность = сумма вкладов:
  положение стержней, концентрация борной кислоты, температурный коэффициент
  (отрицательный), отравление ксеноном-135, самарий.
- Ксеноновая яма: I-135 → Xe-135, периоды 6.6 ч и 9.2 ч. После сброса мощности
  реактор несколько часов невозможно поднять — это отличная игровая механика, а не
  раздражитель, обыграй её.
- Теплогидравлика: тепловая мощность → парогенератор → турбина → электрическая
  мощность, КПД около 33%.
- Выгорание топлива, перегрузка активной зоны, износ оборудования по наработке
  (распределение Вейбулла), регламентное ТО.
- Надзорный орган: пределы безопасной эксплуатации, проверки, предписания, штрафы,
  в пределе — отзыв лицензии и конец партии.

## Персонал — поимённо

- От 30 до 300 именованных сотрудников. У каждого: имя, специальность, квалификация,
  уровень допуска, стаж, усталость, мораль, зарплата относительно рынка, отношения
  с коллегами, риск выгорания.
- Права доступа: матрица «роль × действие», которую настраивает игрок. Слишком
  широкие права — ошибки, нарушения регламента, в пределе саботаж. Слишком узкие —
  простои, некому принять решение в смену, рост недовольства.
- Человеческий фактор: усталая смена ошибается чаще, и это реальная причина аварий
  в модели. Связь «переработки → ошибка → авария → штраф» должна быть прослеживаемой
  в журнале.
- Профсоюз: возникает при накоплении недовольства, выдвигает требования (зарплата,
  графики смен, безопасность, права доступа), переговоры идут раундами, итог —
  коллективный договор. Провал переговоров — забастовка: остановка блока, срыв
  поставок, штрафы. Забастовка должна быть предсказуемой заранее по показателям,
  а не свалиться внезапно.

## Программирование внутри игры — два уровня

Уровень 1, «консоль аналитика». Игра поднимает unix-сокет в $XDG_RUNTIME_DIR.
По клавише из игры запускается `$TERMINAL -e module console` — ОТДЕЛЬНОЕ окно
терминала с настоящим Python REPL, где уже подключён объект `game`, есть история
команд и автодополнение. Никакой песочницы здесь не нужно: это моя машина и мой код.
Определи `$TERMINAL` через переменную окружения с разумными фолбэками, и обязательно
сделай так, чтобы `module console` работал и просто запущенный руками в любом окне.
Через `game` доступна вся телеметрия: временные ряды цен, выработки, показателей
персонала, финансов. Данные отдавай в виде обычных списков и словарей, чтобы их
можно было считать вручную и учиться на этом.

Уровень 2, «автоматизация». Скрипты в `~/.local/share/module/scripts/*.py`, которые
исполняются каждый тик без меня. Вот они обязаны быть изолированы: отдельный процесс,
resource.setrlimit на CPU и память, whitelist AST, таймаут на тик, никакого импорта
кроме разрешённого списка. Скрипт, который завис или упал, отключается с записью в
журнал и никогда не вешает симуляцию.

Плюс серия обучающих заданий: игра ставит задачу («построй распределение цен по часам
и найди, в какие часы маржа максимальна»), проверяет результат и открывает следующий
уровень автоматизации. Это учебная линия, относись к ней как к полноценной части игры.

## Интерфейс

Красивый — это требование, а не пожелание. Вкладки: Реактор (мнемосхема), Экономика,
Персонал, Права, Рынок, Журнал, Аналитика. Живые графики, аккуратная типографика,
единая цветовая тема в theme.tcss, светлая и тёмная. Никаких блокирующих модалок.
Всё управление с клавиатуры, мышь как бонус. Панель времени со скоростью и текущей
игровой датой всегда на виду.
```

## Дальнейшие промпты — по одной фазе за раз

Каждый следующий промпт короткий, потому что спецификация уже в `docs/` и `CLAUDE.md`.

- **Фаза 1.** «Фаза 1 по DESIGN.md: игровое время, тики, догон пропущенного времени с
  прогресс-баром, базовый реактор одной формулой мощности, продажа энергии по
  фиксированной цене, деньги. Плюс система приказов с длительностью. Бенчмарк догона
  в тестах: не меньше 200k тиков/сек.»
- **Фаза 2.** «Фаза 2: экономика. Рынок с суточным и сезонным профилем, споты и PPA,
  топливные контракты с лагом, кредиты со ставкой от рейтинга, банкротство,
  переходящий долг в meta.json, процедура списания. Банкротство не завершается в
  отсутствие игрока: при возвращении даётся срок на исправление (DESIGN.md, §Р5).
  Заодно откалибровать курс догона — теперь видно, на каком горизонте решения
  игрока успевают что-то значить.»
- **Фаза 3.** «Фаза 3: поимённый персонал, генерация людей, квалификация, усталость,
  мораль, смены, матрица прав доступа, влияние прав на простои и ошибки.»
- **Фаза 4.** «Фаза 4: недовольство, профсоюз, требования, раунды переговоров,
  коллективный договор, забастовка. Забастовка обязана быть предсказуемой по
  показателям минимум за несколько игровых суток. Плюс постоянные распоряжения:
  в отсутствие игрока станция работает по ним и по матрице допусков, а без
  распоряжения персонал не рискует и разгружает блок (DESIGN.md, §Р5).»
- **Фаза 5.** «Фаза 5: настоящая физика. Точечная кинетика, ксенон-135 и яма,
  температурный коэффициент, бор, выгорание, износ по Вейбуллу, ТО, надзорный орган.»
- **Фаза 6.** «Фаза 6: скриптинг. Unix-сокет, `module console` в отдельном терминале
  с настоящим REPL, объект game с телеметрией, песочница для автоматизации, первые
  пять обучающих заданий.»
- **Фаза 7.** «Фаза 7: интерфейс. Мнемосхема реактора, графики, темы, полировка всех
  вкладок.»
- **Фаза 8.** «Фаза 8: упаковка. PKGBUILD, установка через makepkg, проверка что
  `module` запускается на чистой системе, релизы и версии.»

## Правила работы, которые сэкономят вам недели

- **Одна фаза — одна ветка — один PR.** Не разрешайте вести две фазы сразу.
- **После каждой фазы просите добавить сейв текущей версии в `tests/fixtures/saves/`.**
  Это единственный способ реально гарантировать, что обновления не ломают прогресс.
- **Баланс держите в `docs/BALANCE.md` и в одном модуле констант**, а не размазанным
  по коду. Иначе настройка сложности превратится в археологию.
- **Требуйте, чтобы каждая новая механика приходила с тестом на детерминизм.**
- **Начинайте играть в свою игру с фазы 2.** Дизайн-ошибки видны только изнутри, и
  чем раньше вы их поймаете, тем дешевле.
- **Не давайте расширять список зависимостей** без проверки, что пакет есть в
  официальных репозиториях Arch.
