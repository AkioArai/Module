# Формат сохранения и правила миграций

**Требование номер один по важности: обновление игры никогда не теряет
прогресс.** Всё в этом документе подчинено ему.

---

## 1. Файлы на диске

Пути по XDG, вычисляются в `module_sim/persistence/paths.py`. Переменные
окружения `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_RUNTIME_DIR` уважаются;
`MODULE_DATA_HOME` перекрывает всё (нужен тестам и для нескольких профилей).

| Путь | Что | Переживает удаление партии |
|---|---|---|
| `~/.local/share/module/save.json` | Текущая партия | нет |
| `~/.local/share/module/save.json.1` … `.5` | Кольцо бэкапов, `.1` — самый свежий | нет |
| `~/.local/share/module/save.json.tmp-*` | Временные файлы записи | — |
| `~/.local/share/module/meta.json` | Метапрогресс между партиями | **да** |
| `~/.local/share/module/scripts/*.py` | Скрипты автоматизации игрока | **да** |
| `$XDG_RUNTIME_DIR/module/console.sock` | Сокет консоли аналитика | — |

`meta.json` содержит переходящий долг, флаги банкротств и сроки их последствий.
Он **никогда не удаляется вместе с партией** — в этом его смысл.

## 2. Структура сейва

```jsonc
{
  "schema_version": 2,          // целое, монотонно растёт
  "created_at": 1765000000.0,   // unix-время создания партии
  "saved_at":  1765003600.0,    // unix-время записи; из него считается догон
  "game": {
    "seed": 1234567890,         // корневой seed партии
    "tick": 8760,               // сколько игровых часов сыграно
    "epoch": 1765000000.0,      // unix-время, соответствующее tick == 0
    "speed": "x1",              // paused | x1 | x5 | x50
    "company": { "name": "...", "cash_cents": 5000000000 },
    "rng": { "counters": { "market.noise": 8760, "people.names": 300 } }
  }
}
```

Ключевые правила структуры:

- `schema_version` — **целое**, растёт ровно на единицу за миграцию. Не
  семантическая версия, не строка, не версия приложения.
- Всё под `game` — состояние симуляции, сериализуемое из dataclass-ов
  `core/state.py`. Всё вне `game` — метаданные контейнера.
- Ключи полей — английские `snake_case` (см. DESIGN.md, §Р4): их читает
  скриптовый уровень.

### Числа

- **Деньги — целые копейки** (`*_cents`). Float для денег запрещён: он ломает
  балансовое тождество на длинных партиях и делает диффы фикстур
  нестабильными.
- Физические величины — `float`. Детерминизм обеспечивается фиксированным
  порядком операций, а не округлением (см. CLAUDE.md).
- Время партии — целый `tick` (игровых часов), не дата. Календарь выводится из
  `epoch + tick`.

### Состояние RNG

Сериализуются **счётчики потоков**, а не внутреннее состояние генератора. Поток
восстанавливается как чистая функция `(seed, имя потока, счётчик)`. Это
принципиально: добавление нового потока в новой версии игры не сдвигает
последовательности существующих, и старые сейвы продолжают считаться так же
(см. `core/rng.py` и CLAUDE.md, §Детерминизм).

## 3. Кодек

Ввод-вывод спрятан за `persistence/codec.py`. Сейчас умолчание — **JSON**:
читаемый глазами сейв дороже экономии байт, пока мы отлаживаем цепочку миграций
и держим фикстуры в git.

Кодек выбирается по расширению файла: `.json` → JSON, `.msgpack` → msgpack.
Оба пути реализованы и покрыты тестами с первого дня.

**Критерий переезда на msgpack**: сейв стабильно больше ~5 МБ или запись
занимает больше ~50 мс. Переезд — это смена умолчания плюс одна миграция; сейвы
не теряются, потому что загрузка определяет кодек по существующему файлу.

JSON пишется с `sort_keys=True`, `ensure_ascii=False` и отступом 1 — так диффы
фикстур в git читаемы, а порядок ключей не зависит от порядка вставки.

## 4. Атомарная запись

Порядок операций в `save.py`, менять нельзя:

1. Сериализовать в память (ошибка сериализации не должна тронуть файл на диске).
2. Записать во временный файл `save.json.tmp-<pid>-<counter>` в **том же
   каталоге** (иначе `os.replace` перестанет быть атомарным — другое
   устройство).
3. `f.flush()`, затем `os.fsync(f.fileno())` — данные на диске, не в кэше.
4. Провернуть кольцо бэкапов: `.4→.5`, `.3→.4`, `.2→.3`, `.1→.2`, затем текущий
   `save.json` → `.1` **жёсткой ссылкой** (`os.link`), а не переименованием.
   Переименование оставило бы окно, в котором `save.json` не существует вовсе;
   ссылка не копирует данные и такого окна не создаёт. На файловой системе без
   жёстких ссылок — честная копия.
5. `os.replace(tmp, save.json)` — атомарная подмена на POSIX. Новый файл
   получает имя `save.json`, старый инод продолжает жить под именем `.1`.
6. `os.fsync` на дескрипторе **каталога** — чтобы сама операция переименования
   дошла до диска.

Гарантия: в любой момент, включая обрыв питания, `save.json` — это либо целиком
старая версия, либо целиком новая. Битого файла получить нельзя. Временные
файлы, оставшиеся от прерванной записи, подчищаются при следующем сохранении.

### Восстановление

`module save restore [N]` берёт `save.json.N` (по умолчанию `.1`) и ставит его
текущим — через ту же атомарную процедуру.

Загрузка при повреждении `save.json` (не разбирается или не проходит миграции)
автоматически пробует бэкапы по порядку `.1`…`.5`, пишет в журнал, какой файл
взят, и продолжает игру. Молча терять партию нельзя.

## 5. Миграции

### Правила

1. Каждое изменение структуры — **новый файл** `migrations/vNNN.py` с функцией
   `migrate(data: dict) -> dict`, поднимающей версию **ровно на единицу**.
2. **Старую миграцию никогда не редактируют.** Только добавляют новую. Правка
   `v003.py` после релиза ломает сейвы тех, кто уже через неё прошёл.
3. При загрузке применяется вся цепочка от версии файла до текущей, по одной
   версии за шаг.
4. Миграция получает и возвращает **обычный dict**. Она не импортирует
   `core/state.py`: dataclass-ы меняются, а миграция обязана работать вечно с
   тем, что было в файле на её момент.
5. Миграция не имеет права упасть на данных своей версии. Отсутствующее поле —
   значение по умолчанию, а не исключение.
6. Сейв версии **выше** текущей не загружается: это откат игры назад, и молча
   портить файл нельзя. Игроку сообщается, что нужна версия новее.

### Как добавить миграцию

```bash
# 1. Зафиксировать сейв ТЕКУЩЕЙ версии как фикстуру — до изменения кода
.venv/bin/python -m module_sim.cli save export tests/fixtures/saves/vNNN.json
```

2. Изменить `core/state.py`.
3. Поднять `CURRENT_SCHEMA_VERSION` в `persistence/migrations/__init__.py`.
4. Создать `migrations/vNNN.py`, где `NNN` — **новая** версия:

```python
"""vNNN: краткое описание изменения."""

FROM_VERSION = NNN - 1
TO_VERSION = NNN

def migrate(data: dict) -> dict:
    game = data["game"]
    game["new_field"] = game.pop("old_field", DEFAULT)
    return data
```

5. Прогнать `pytest tests/test_migrations.py` — тест сам обнаружит новую
   фикстуру и прогонит её через всю цепочку.

Цепочка собирается автоматически: `migrations/__init__.py` сканирует модули
`vNNN`, проверяет, что версии идут подряд без дыр, и что последняя совпадает с
`CURRENT_SCHEMA_VERSION`. Дыра или расхождение — падение тестов, не рантайма.

## 6. Фикстуры — главный страж требования

В `tests/fixtures/saves/` лежат **настоящие сейвы каждой версии**, какими их
писала игра на момент этой версии. Не синтетические, не подправленные руками.

`tests/test_migrations.py` для каждой фикстуры:

1. Загружает файл.
2. Прогоняет всю цепочку миграций до текущей версии.
3. Проверяет, что результат разбирается в `GameState`.
4. Проверяет, что симуляция **идёт дальше**: несколько тиков без исключений.
5. Проверяет, что сохранение результата и повторная загрузка дают то же
   состояние (round-trip).

Это и есть автоматическая проверка обещания «обновление не теряет прогресс».
Фикстуры **никогда не удаляются** — даже фикстура v001 будет прогоняться через
всю цепочку и через год.

---

## 7. Обратная совместимость и чего мы не обещаем

Обещаем: любой сейв, созданный любой выпущенной версией игры, загрузится в
текущей.

Не обещаем: что сейв из новой версии откроется в старой (см. §5, правило 6), и
что игровой смысл сохранится дословно. Если баланс изменится, партия продолжится
по новым правилам — деньги, штат, износ и долг переносятся, но экономика может
стать другой. Миграция обязана сохранить **прогресс**, не **баланс**.
